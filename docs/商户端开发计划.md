# 商户端开发计划

> 记录时间：2026-09-16
> 代码范围：`code-scaffold/`（Spring Boot 3.5.7 + Vue 2 + MySQL）
> 前提：本文基于对当前代码的静态核对（已确认全仓库无任何 merchant/商户/店铺 相关代码，商户端确为从零新增）。
> 配套文档：`待修复与待办.md`（安全与已知 Bug 清单，本文不重复展开）

**一句话结论**：商户端不是"再加一套页面"，而是**加第三个角色 + 把商品所有权从 `admin` 剥离**。
真正的工作量在数据模型（商品归属、订单拆单），页面反而是最轻的一环。

---

## 一、现状：商户端现在插不进去的三个卡点

### 当前三端实况

| 端 | 入口 | 身份来源 | Token 签发 | Token 校验 | 能做什么 |
| --- | --- | --- | --- | --- | --- |
| 管理端 | `/` → `Manager.vue` | `admin` 表 | `/admin/login`，密钥 `ADMIN_TOKEN_SECRET`（硬编码） | `JwtInterceptor:84-95`，用管理密钥验签 | 全量：用户/管理员/分类/商品/订单/轮播/收藏 |
| 用户端 | `/front` → `front/Front.vue` | `user` 表 | `/login` | `JwtInterceptor:107`，**用用户密码当 HMAC 密钥** | 浏览、收藏、购物车（本地）、下单、支付 |
| 商户端 | — | — | — | — | **不存在** |

### 卡点 1：身份体系是三套拼起来的，加第四套会散架

- `JwtInterceptor` 里管理员和普通用户走**两条完全不同的验签分支**（`JwtInterceptor.java:84-95` vs `:104-112`）；
- 而 `TokenUtils.getCurrentUser()` 走的是**第三条路**——`JWT.decode()` 只解 base64、**不验签**（`TokenUtils.java:107`）；
- 于是「我是谁」在不同接口里有两种答案：`OrdersServiceImpl.selectPage` 用 `TokenUtils`（可伪造），`/admin/**` 用拦截器（安全）。

**商户端会立刻放大这个问题**：商户 A 能不能改商户 B 的商品，取决于商户接口用的是哪条取值路径。
所以**统一身份解析是商户端的第一道工序，不是可选项**（对应 Phase 0）。

### 卡点 2：商品归属目前挂在管理员身上

`goods.admin_id` 是全项目唯一的「商品归属」字段：

```java
// GoodsServiceImpl.java:41
goods.setAdminId(TokenUtils.getCurrentUser().getId());
// GoodsServiceImpl.java:92  列表里反查归属人名
Admin admin = adminMapper.selectById(goods.getAdminId());
```

**这其实说明：现在的 `admin` 就是"唯一的大商户"** —— 8 条种子商品的 `admin_id` 全是 1。
商户端要做的本质就是：**把商品所有权从 `admin` 表剥离到 `merchant` 表**。
`admin` 退化为「平台运营方」，只保留审核、总览、干预能力。

### 卡点 3：订单是单商户模型，跨商户购物车会撞车

| 位置 | 现状 | 商户端要求 |
| --- | --- | --- |
| `Orders.java:17` | 一个订单只有一个 `goodsId` | 订单要带 `merchant_id` |
| `orders` 表 | 无 `merchant_id` | 商户只能看自己的订单 |
| `order_item` 表 | `order_id/goods_id/goods_name/price/nums`，**无商户维度** | 明细要能定位到商户 |
| `OrdersServiceImpl.settle()` | 一次结算生成 **1 张订单 + N 条明细**（`:90-106`） | 购物车跨商户必须拆成 M 张订单 |
| `OrdersServiceImpl:184` | 详情只反查主商品 `orders.getGoodsId()` | 拆单后主商品语义要重定 |

> 补充：`settle()` 已经写得比旧版 `save()` 好（服务端算价、`deductStore` 原子扣库存、有 `@Transactional`），
> 拆单改造可以在这个方法基础上做，不用推倒重来。

## 二、必须先定的三个设计决策

### D1 商户身份怎么存？

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 复用 `user` 表加 `role='MERCHANT'` | 改一行枚举 | ❌ 商户有店铺名/logo/营业执照/审核状态/结算账户等一堆专属字段，全塞 `user` 表会污染；且现有 `user` 表被 `/login`、`selectByUsername(username, role)` 深度绑定 |
| B. 独立 `merchant` 表 + 独立登录入口 | 与 `admin` 完全对称 | ✅ **推荐** |

**推荐 B，理由**：`admin` 已经开了「独立表 + 独立登录 + 独立密钥」的先例，商户照着做成本最低、语义最干净。

**代价（要老实说）**：Token 体系会出现**第三个密钥**。
`TokenUtils` 目前是 `ADMIN_TOKEN_SECRET`（硬编码）+ 用户密码两种密钥混用；
再加商户密钥会让 `JwtInterceptor` 变成三分支 if-else —— 这不可接受。

→ **所以 D1 必须和 Phase 0 的「统一身份解析」一起做**：收敛成**一个全局密钥 + `role` 声明**，
`getCurrentUser()` 改为从拦截器写入的 request attribute 取值。这一步做完，将来加第四个角色是零成本。

---

### D2 商品归属用 `admin_id` 还是新增 `merchant_id`？

**推荐：新增 `goods.merchant_id`，`admin_id` 保留但降级**。

- `merchant_id` → 商品归哪个商户（商户端只查 `where merchant_id = 当前商户`）
- `admin_id` → 保留为「录入人/代运营管理员」，平台代录商品时 `merchant_id` 为平台自营商户

**影响面（改动点已定位）**：

| 文件 | 改动 |
| --- | --- |
| `Goods.java:22` | 加 `private Integer merchantId;` |
| `GoodsServiceImpl.java:41` | `setAdminId` → 按登录角色决定写 `merchantId` 还是 `adminId` |
| `GoodsServiceImpl.java:92,124` | 归属人反查从 `adminMapper` 换成 `merchantMapper`（顺带修掉「添加人列永远是空」的老 Bug） |
| `manager/Goods.vue:31,138` | 列名/字段名对齐（`adminName` → `merchantName` 或双列并存） |
| `sql` 迁移 | 加列 + `idx_goods_merchant_id` + 存量 8 条商品回填到种子商户 |

---

### D3 跨商户订单怎么拆？——**这个决策最容易做错，重点看**

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 一张订单，明细挂 `merchant_id` | `order_item` 加列即可 | ❌ **订单主状态无法表达**。商户 A 发货了、商户 B 没发，`orders.state` 该写什么？商户侧「发货」只能做到明细粒度，`manager/Orders.vue` 的状态流转全废 |
| B. 按商户拆单 | 结算时按 `merchant_id` 分组，每个商户生成一张 `orders` | ✅ **推荐** |

**推荐 B**，具体：

```
用户一次结算（3 个商户的 5 件商品）
    ↓ OrdersServiceImpl.settle() 按 merchant_id 分组
    ├── 订单 #101  merchant_id=1  parent_no=B20260916xxx  → 2 条 order_item
    ├── 订单 #102  merchant_id=2  parent_no=B20260916xxx  → 2 条 order_item
    └── 订单 #103  merchant_id=3  parent_no=B20260916xxx  → 1 条 order_item
```

- `orders` 加 `merchant_id` + `parent_no`（同一批次号，「我的订单」页仍按批次聚合展示给用户）
- 每个商户独立走 `待付款 → 已支付 → 已发货 → 已完成`，互不阻塞
- 支付要支持**批量付一批**（用户视角是一个操作，服务端循环扣 M 张订单的钱）—— 这块要注意事务边界
- **副作用要提前想好**：`orders` 的 `goods_id`/`name`/`price`/`nums` 是单商品时代遗留字段，
  拆单后建议明确语义为「本单主商品 + 本单小计」，或直接逐步废弃，改由 `order_item` 承载

## 三、分阶段实施计划

### Phase 0 — 前置治理（**阻塞项，必须最先做**）

> 不做这一步，后面所有商户接口都是在漏洞上加楼层：现在 `/goods/**`、`/orders/**` 是**匿名全放行**的
> （`InterceptorConfig.java:18-19`），商户接口如果照抄这个写法，等于所有商户数据互相可见。

| # | 改动 | 位置 | 验收 |
| --- | --- | --- | --- |
| 0.1 | 放行名单收敛，匿名接口改用 `@AuthAccess` 标注 | `InterceptorConfig.java:18-19` | 无 token 访问 `/goods/selectPage` 返回 401 |
| 0.2 | **统一身份解析**：拦截器验签后把身份写入 `request.setAttribute`；`TokenUtils` 改为只读 attribute，删除 `JWT.decode` 路径 | `TokenUtils.java:60-111`、`JwtInterceptor.java` | 伪造 token 访问 `/collect/myCollect` 返回 401 |
| 0.3 | 全局密钥收敛为**一个** + `role` 声明，密钥移入 `application.yml` | `TokenUtils.java:28,42-58` | `/admin/login` 签发的 token 能被正常验签（修掉 P0-4） |
| 0.4 | 加**角色 + 数据归属**双重校验：`/admin/**` 仅 ADMIN；`/orders/**`、`/collect/**` 限本人 | `JwtInterceptor.java` | tom 的 token 调 `/admin/selectAll` 返回 403 |
| 0.5 | `OrdersServiceImpl:178` 的 `currentUser.getRole().equals("USER")` 补判空（当前唯一的行级隔离，NPE 即绕过） | `OrdersServiceImpl.java:177-180` | — |

**这一层做完，商户端只需要在 0.4 的规则表里加一行 `/merchant/**` → `MERCHANT`，不用再碰认证代码。**
这也是为什么它必须排在前面 —— 它是唯一能「一次做对、后面零成本」的改动。

### Phase 1 — 数据模型

产出：一份可重复执行的迁移脚本 `sql/migration_merchant.sql`（与现有 `code_scaffold.sql` 风格一致）。

```sql
-- 1. 商户表
CREATE TABLE `merchant` (
  `id` int NOT NULL AUTO_INCREMENT,
  `username` varchar(255) NOT NULL COMMENT '登录名',
  `password` varchar(255) NOT NULL,
  `shop_name` varchar(255) NOT NULL COMMENT '店铺名称',
  `logo` varchar(500) DEFAULT NULL COMMENT '店铺LOGO',
  `descr` varchar(500) DEFAULT NULL COMMENT '店铺简介',
  `phone` varchar(255) DEFAULT NULL COMMENT '联系电话',
  `address` varchar(255) DEFAULT NULL COMMENT '经营地址',
  `license` varchar(500) DEFAULT NULL COMMENT '营业执照图片',
  `state` varchar(50) NOT NULL DEFAULT '待审核' COMMENT '入驻状态：待审核/已通过/已驳回/已停用',
  `reject_reason` varchar(255) DEFAULT NULL COMMENT '驳回原因',
  `account` decimal(10,2) NOT NULL DEFAULT 0 COMMENT '可结算余额',
  `create_time` varchar(50) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_merchant_username` (`username`)
) COMMENT='商户表';

-- 2. 商品加归属商户
ALTER TABLE `goods` ADD COLUMN `merchant_id` int DEFAULT NULL COMMENT '归属商户ID';
ALTER TABLE `goods` ADD KEY `idx_goods_merchant_id` (`merchant_id`);

-- 3. 订单加商户 + 结算批次
ALTER TABLE `orders` ADD COLUMN `merchant_id` int DEFAULT NULL COMMENT '归属商户ID';
ALTER TABLE `orders` ADD COLUMN `parent_no` varchar(50) DEFAULT NULL COMMENT '同批次结算号（跨商户拆单用）';
ALTER TABLE `orders` ADD KEY `idx_orders_merchant_id` (`merchant_id`);
ALTER TABLE `orders` ADD KEY `idx_orders_parent_no` (`parent_no`);

-- 4. 明细加商户（冗余，便于商户侧直查，不用 join orders）
ALTER TABLE `order_item` ADD COLUMN `merchant_id` int DEFAULT NULL;
ALTER TABLE `order_item` ADD KEY `idx_order_item_merchant_id` (`merchant_id`);

-- 5. 存量数据迁移：现有 8 条商品归属 admin_id=1，建一个种子商户承接
INSERT IGNORE INTO `merchant` (id, username, password, shop_name, state, create_time)
VALUES (1, 'shop_demo', '123', '捞宝自营旗舰店', '已通过', '2026-09-16 00:00:00');
UPDATE `goods` g SET g.merchant_id = 1 WHERE g.merchant_id IS NULL AND g.admin_id IS NOT NULL;
```

同时定义**订单状态字典**（后端常量类 + 前端常量文件，别再散字符串）：

```
待付款 → 已支付 → 已发货 → 已完成
  └→ 已取消（待付款时）
  └→ 退款中 → 已退款（Phase 4）
```

### Phase 2 — 后端

**新增（全部约束 `merchant_id = 当前登录商户`，这是硬要求）**

| 模块 | 接口 | 说明 |
| --- | --- | --- |
| 登录 | `POST /merchant/login`、`POST /merchant/register` | 注册后 `state='待审核'`，审核通过才能上架 |
| 店铺 | `GET/PUT /merchant/profile` | 店铺信息维护、LOGO 上传（复用 `FileController`） |
| 商品 | `/merchant/goods/{selectPage,add,update,delete,onOff}` | 复用 `GoodsServiceImpl` 逻辑 + 强制注入归属校验；`onOff` 取代现在的整行 PUT 改状态 |
| 订单 | `/merchant/orders/selectPage`、`/detail`、`POST /ship` | `selectPage` 强制 `merchant_id` 过滤；`ship` 是**专用状态流转接口** |
| 概览 | `GET /merchant/stats` | 待发货数、今日订单/销售额、库存预警、总销量 |
| 结算 | `GET /merchant/settle/list` | Phase 4，先留位 |

**改造**

| 文件 | 改动 |
| --- | --- |
| `OrdersServiceImpl.settle()` | 按 `merchant_id` 分组拆单；写 `merchant_id`/`parent_no`；同时修掉 `price>0` 校验、订单归属校验 |
| `OrdersServiceImpl.pay()` | 支持批量付一个 `parent_no` 下的多张订单；`userId` 取自登录态、`price` 服务端重算（顺带修掉「能造钱」的 P1-1） |
| `OrdersServiceImpl.update()` | 禁止前端直接 PUT 整行改 `state`，改为只允许专用流转接口 |
| `GoodsServiceImpl` | 归属校验抽成公共方法，商户端与管理端复用 |
| `AdminController` / 新增 `MerchantAdminController` | 平台侧：商户列表、**审核通过/驳回**、停用；平台总览订单按商户维度出数 |

**关键实现约定（避免重蹈现有代码覆辙）**

1. 商户端每一个查询/写入都必须带 `merchant_id` 条件，且该值**只能取自登录态**，绝不能从请求参数读
2. 越权校验放在 Service 层而不是 Controller —— 现在 `AdminController.delete` 只有 Controller 层自检，是可绕过的
3. 状态流转走专用接口 + 前置状态校验（如：只有 `已支付` 才能发货），不要复用 `update`

### Phase 4 — 入驻与资金（可选，视需求取舍）

- **入驻审核流**：商户注册 → 平台审核 → 通过后自动创建登录账号（现在是先建号后补资料）
- **商户收益**：订单完成后按比例计入 `merchant.account`，平台佣金率可配
- **提现申请**：商户发起 → 平台审核 → 打款（**只做台账，不接真实支付通道**）
- **对账单**：按日期/商户导出结算明细

> 建议：本期**先不做 Phase 4**。真实支付通道、分账、发票都会把项目复杂度抬一个量级，
> 而「账面收益统计」在演示/验收场景下信息量已经够。

## 四、优先级与依赖

| 阶段 | 规模 | 阻塞关系 | 理由 |
| --- | --- | --- | --- |
| Phase 0 前置治理 | **M**（≈8 个文件） | 无，**最先做** | 唯一「一次做对、后面零成本」的改动；不做则 Phase 2 全部返工 |
| Phase 1 数据模型 | **S** | 依赖 D1/D2/D3 拍板 | 一个 SQL 文件，但决策错了后面全错 |
| Phase 2 后端 | **L** | 依赖 0、1 | 工作量主体，实体/Mapper/Service/Controller 四件套 × 6 个模块 |
| Phase 3 前端 | **M** | 依赖 2 | 大量复用现有页面，是四阶段里性价比最高的 |
| Phase 4 进阶 | **L** | 依赖 3 | 可延后，不影响商户端主链路闭环 |

**建议执行顺序**：`D1/D2/D3 拍板` → `Phase 0` → `Phase 1` → `Phase 2` → `Phase 3` → （Phase 4 另议）

## 五、本期明确不做

- ❌ 真实支付通道、提现打款、分账对账、发票（Phase 4 另议，只做台账）
- ❌ 店铺装修 / 多套店铺模板 / 店铺独立二级域名
- ❌ 商品 SKU 多规格（当前 `goods` 是单品模型，加 SKU 是独立工程量，与商户端解耦）
- ❌ 商户客服 / 站内 IM
- ❌ 物流轨迹对接（发货只记运单号，不接快递 100 / 菜鸟）
